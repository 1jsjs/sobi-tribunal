# 제출용 "Kiro 활용" 답변 (≤2000자, v3 리포 기준 — 실물과 일치하는 내용만)

⚠️ Hooks 문단은 `.kiro/hooks/`에 훅이 실제로 생성된 뒤에만 포함할 것.

---

**Steering — 프로젝트 헌법을 상시 주입 (.kiro/steering/ 4종)**

제품 정의(product)·기술 제약(tech-constraints)·리포 구조(structure)·API 계약(api-contract)을
steering 문서로 고정해 Kiro의 모든 작업에 자동 포함시켰습니다. 특히 tech-constraints에는
실측으로 당한 함정을 규칙으로 박았습니다: Bedrock Claude(Sonnet 5) 응답의 첫 블록이
thinking일 수 있어 content[0] 직접 접근 금지, temperature/top_p 전송 시 ValidationException,
FastAPI 선검증이 내는 422를 전역 핸들러로 400 응답 봉투에 강제 변환, 그리고 로컬 검증
사다리(①mock: 룰·계약 → ②Gemini 무료 API: 같은 프롬프트·같은 JSON 파싱 경로로 LLM 거동
검증 → ③배포 후 Bedrock 실측·로그 확인). 효과: 태스크 프롬프트마다 제약을 반복 설명하지
않아도 Kiro가 계약과 함정을 지킨 코드를 대부분 첫 시도에 생성했습니다.

**Specs — 문서 스펙을 태스크로 분해**

판정 룰표(심문 질문 뱅크 8문과 선택지별 축·유죄 태그, 소비유형 16종, 점수 컷)·LLM 프롬프트
3종(비전 조서/질문 재작성/판결문)·API 계약을 docs/에 설계 스펙으로 고정하고,
kiro-prompts/에 태스크 10개(B301~B305 백엔드, F301~F305 프론트)로 분해해 문서화했습니다.
"한 번에 한 태스크, 항상 실행 가능한 상태 유지" 원칙으로 진행했고, 각 프롬프트에 완료
기준(uvicorn 기동, pytest green, 검증 명령)을 명시해 Kiro가 스스로 확인하게 했습니다.
핵심 설계 원칙 "판정은 룰, 문장은 LLM"도 스펙에 고정해, LLM 전면 장애 시에도 재판이
끝까지 진행되는 구조를 Kiro가 일관되게 유지했습니다.

**사람 교차검증 루프**

Kiro 산출물은 태스크마다 코드 리뷰 + 테스트 + 실측으로 교차검증한 뒤 커밋했습니다.
실제로 잡아 고친 사례: ①검증 전용 엔드포인트가 프로덕션 코드에 남아 금지 패턴(typed
body)이 이후 작업의 참고 코드가 될 뻔한 것 → 테스트 전용으로 이전 ②SQLite ALTER
마이그레이션이 비상수 DEFAULT 컬럼을 처리하지 못하는 잠재 버그 → 구버전 DB 시뮬레이션
으로 재현·수정 ③신규 API 키에서 기본 Gemini 모델이 마감돼 404가 나는 문제 → 실호출로
확인 후 모델 교체. 이 검증 루프 자체가 steering의 함정 목록을 갱신하는 입력이 됐습니다.

**Hooks** *(훅 생성 후 포함)*

services/·constants.py 저장 시 pytest를 자동 실행하는 훅으로 판정 룰·LLM 요청 계약의
회귀를 저장 즉시 감지하도록 했습니다.
