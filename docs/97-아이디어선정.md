## 서비스명

소비 재판소

## 한줄소개

후회되는 소비의 사진 한 장을 '기소'하면 AI 판사가 심문하고 유·무죄를 선고하는 웹 법정 —
재판 과정에서 자신의 소비를 회고하고, 소비 유형(16종)과 절약 미션(형량)을 받아
근거 있는 소비로 이어지게 하는 서비스

## 문제정의

최근 MBTI, 사주 등 자신의 성향을 분석하고 타인과 공유하는 서비스가 큰 인기를 끌고
있습니다. 이는 타인을 이해하기 점차 어려워지는 현대 사회에서, 나를 적극적으로 표현하고
서로를 알아가고자 하는 대중의 심리적 기조가 반영된 결과입니다.

저희는 이러한 트렌드에 착안하여, 단순한 수입과 지출의 나열에서 벗어난 새로운 형태의
서비스 **'소비 재판소'**를 제안합니다. 사용자의 소비 내역을 분석해 개인의 지출 성향을
파악하고, 여기에 '재판과 판결'이라는 엔터테인먼트 요소를 결합했습니다.

특히, 사용자는 LLM(거대 언어 모델)과 소통하며 과거 자신의 소비 행동이 정당했는지
변론하고 판결을 받는 과정을 거치게 됩니다. 이 흥미로운 상호작용을 통해 사용자는
스스로의 지출을 돌아보고 올바른 소비 기준을 다잡는 깨우침을 얻게 됩니다.

결과적으로 '소비 재판소'는 사용자들이 서로의 소비 성향을 즐겁게 공유하고 기록하게
만들며, 궁극적으로는 자발적인 소비 절약을 이끌어내는 긍정적인 트리거 역할을 할 것입니다.

## 핵심기능

1. 출석 · 기소
- 비밀번호 없이 이메일만 입력해 피고인으로 출석한다.
- 결제내역 캡처·영수증·제품 사진 중 한 장을 올려 후회 소비 한 건을 기소한다.

2. 조서 작성 (LLM)
- Bedrock 비전이 사진에서 품목·가격·날짜를 뽑아 조서를 만든다.
- 캡처에 거래가 여러 건이면 어느 건으로 기소할지 고를 수 있다.
- 사용자가 조서를 수정 가능한 카드로 확인한 뒤에만 재판에 쓴다.

3. 심문 (법정 화면)
- 판사가 질문 6~8개를 하나씩 던지고, 사용자는 선택지를 탭해 답한다.
- 질문 문구는 Bedrock이 그 물건에 맞게 재작성한다(금액·품목을 콕 집어 심문).
- 판사 음성은 브라우저 Web Speech API로 낭독한다.
- 올린 사진이 "증거물 제1호"로 걸리고, 답할 때마다 심증 게이지가 차오른다.

4. 판결 · 선고
- 유죄/집행유예/무죄 도장이 찍힌다.
- 판결문이 죄명·주요 증거·재판부 판단·최종 판결의 구조로 낭독되고,
  소비 MBTI 16유형 카드와 형량(절약 미션)이 선고된다.
- 최후 변론을 남기면 판결문에 인용되어 참작 또는 기각된다.

5. 전과 기록
- 판결받은 소비들이 이메일 앞으로 아카이브에 쌓인다.
- 각 기록에서 당시의 심문 문답과 판결문을 다시 볼 수 있다(소비 회고 아카이브).

6. 설계 원칙
- 판정(유·무죄, 16유형, 형량)은 전부 서버의 룰이 결정하고, LLM은 문장만 쓴다
  — 재현 가능하고 조작 불가능한 판결.
- 멀티모달 LLM은 세 곳에서만 쓴다: ①사진→조서 추출 ②질문 재작성 ③판결문 생성.
- LLM이 전부 실패해도 기본 질문 뱅크와 템플릿 판결문으로 재판은 끝까지 진행된다.

## AWS 활용 서비스

1. Amazon Bedrock
- 용도: AI 판사의 언어 생성. Claude Sonnet 5를 invoke_model로 호출.
- 사용하는 곳: ①사진→조서 추출(비전) ②심문 질문을 그 물건 맞춤으로 재작성 ③판결문 생성.
- 판정에는 관여하지 않으며, 실패 시 폴백으로 재판이 계속된다.

2. Amazon S3
- 용도: 기소 사진(증거물) 저장·조회. presigned URL로 전과 기록에서 다시 보여준다.

3. Amazon EC2
- 용도: 앱 배포·구동 (FastAPI + SQLite).

## Kiro 활용

1. Steering — 규칙을 미리 적어둔다
- .kiro/steering/ 폴더에 규칙 문서 4장(제품 정의·기술 제약·구조·API 계약)을 넣어두면
  Kiro가 일할 때마다 자동으로 준수한다.
- 특히 직접 겪은 실수(Bedrock 응답 파싱, 응답 길이 잘림, 에러 처리 방식)를 규칙으로
  적어 같은 실수를 반복하지 않게 했다.

2. Specs — 큰 일을 작은 조각으로 쪼갠다
- 만들 기능을 설계 문서(판정 룰표·프롬프트·API 계약)로 고정하고,
  백엔드 8개·프론트 7개, 총 15개 태스크로 나눴다.
- 한 번에 한 조각씩만 시키고, 항상 돌아가는 상태를 유지했다.
- 각 태스크마다 "이거 되면 완료" 기준(서버 기동, 테스트 통과, 검증 명령)을 적어
  Kiro가 스스로 확인하도록 구성했다.

3. 최종 검수는 사람이
- Kiro가 짠 코드는 사람이 읽어보고, 테스트를 돌리고, 실제로 써본 뒤에만 저장했다.
- 검수에서 잡은 실수는 다시 1번(Steering) 규칙에 추가했다.

4. Hooks — 저장 즉시 자동 회귀 검사
- 판정 룰과 LLM 계약이 걸린 파일(services/, routes/, constants.py, db.py)을 저장하면
  Kiro 훅이 전체 테스트(pytest, MOCK 모드)를 자동 실행한다.
- 판정 룰 테스트는 룰표 문서의 숫자에 잠겨 있어, 코드를 고치다 판정이 1점이라도
  달라지면 저장하는 순간 실패로 잡힌다.
- 훅이 잡은 실수는 다시 Steering 규칙으로 추가된다 — 실수가 재발하지 않는 순환 구조.
